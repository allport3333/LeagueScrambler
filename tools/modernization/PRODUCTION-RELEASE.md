## Database gate

The release requires the additive Account Recovery baseline even though later recovery template and code changes do not require additional DDL. Apply-ProductionAccountRecovery.sql is derived from the existing Development schema. It adds `dbo.User.SessionVersion int NOT NULL DEFAULT (0)` and creates `dbo.AccountRecoveryRequest` with its primary key and user/creation and contact/creation indexes. It copies no rows from Development and contains no data changes to players, memberships, schedules, saved scrambles, assignments or scores. Legacy schedule and scoring objects must already exist. Compare the production-clone schema with the mapped objects before release and do not apply the old EF migration chain automatically.

Record the expected SQL Server identity and database from the approved production configuration. Rehearse from a restored backup with target values set to that clone. Verify column types, nullability, default, primary key and both index definitions, along with pre/post counts and constraints on existing application tables. For an already migrated target the script stops without changing anything. Compare its schema to the expected definitions before marking the step satisfied. Treat a mixed or incompatible state as a stop condition. The script has not been executed against production or a clone in this run.

For release, pause writers, take a fresh database backup and verify it with checksums and a restore rehearsal. Keep the backup location restricted. Apply the reviewed script only after deployment authorization. Return the previous app to service with the additive schema retained only if that pairing passes clone smoke tests, including login/reset and legacy account inserts with the default column. After account recovery or email changes, the old app cannot enforce SessionVersion. An app-only rollback then needs a separately verified session invalidation strategy, including protection against reuse of old cookies. Prefer a compatible fix-forward when changes after cutover must be preserved. A coordinated database restore requires a write freeze and explicit reconciliation of any post-backup records. Preserve recovery audit data for any rollback and avoid dropping the new schema as a routine step.

## Cutover and rollback checklist

1. Export current IIS site, binding and pool configuration. Record the live physical path, TLS binding, identity, secret references and persisted Data Protection location. Snapshot the current application files to a restricted, immutable rollback location and verify their manifest.
2. Require a verified database backup, restore rehearsal, signed-off schema plan and successful package acceptance. No backup, production inventory or deployment was taken or verified in this run.
3. With explicit authorization, stage a complete verified release in a separate folder. Validate it before atomically switching the site or deployment slot to the new tree. Prevent writers during the schema and cutover window. Avoid copying files over the live worker manifest or a running application's assets.
4. For rollback, prepare a copy of the backed-up app and configuration and follow the verified schema/session decision above. Give the previous browser assets a new worker manifest identity with a unique release identifier in `appData`. An installed worker can ignore a manifest version it has already seen. Verify all asset hashes and regenerate the rollback package's integrity manifest before switching the site. Keep old fingerprinted assets available through the transition when the deployment mechanism supports serving them without exposing old secrets or API code.

## PWA and production smoke

Run the two-build and original-worker upgrade harness before cutover. Test that the manifest and worker revalidate, hashed assets remain cacheable, and API results are no-store. Verify promotion and rollback with complete packages. On Chrome desktop and native Android and iOS installations, open the old installed app before release, then cold-launch and resume after cutover, reconnect after offline, and confirm the new version loads while preserving route and theme. Check that an in-progress score entry defers reload until safe. Browser automation and native device results should be recorded separately.

Immediately verify homepage, mobile navigation and all three themes, worker/manifest requests and console/server logs. Use designated accounts to verify Admin, Manager and Player login and league scope. Check league switching, schedule and standings, Scrambler generation without saving to an existing league, Team Scores rendering and access to historical records. Use approved isolated accounts or fixtures for registration, player claiming, account recovery and reset mail. Confirm approved mailbox receipt separately from transport acceptance. Never approve or alter a real account merely to smoke-test. Watch IIS errors, application logs and API health during the rollback window.
